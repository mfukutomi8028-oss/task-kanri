# JOURNAL 業務手帳の4画面設計

2026-11-19。対象は表示モード JOURNAL。利用者が朝に仕事を選び、案件を進め、空き時間を調べ、記録を引き直すまでを検討した。以下の操作数は受け入れ目標。実測結果は実装・検証の記録で判定する。

## 構成の選択

起点は Ver.654 の main、コミット `e24a0eda5d44a89487bcd023faec8a57795bb94e`。PR #975 のメモ削除後の復帰と #983 の公開を含む。既存のテストには、今日の読み順、予定・メモから案件への往復、取り消し、競合時の下書き保持、キーボードフォーカスの復元がある。タスクと予定の編集には既存のダイアログと保存経路を使う。

| 優先度 | 利用者への影響と対応 | 変更の影響・検証 |
| --- | --- | --- |
| P0 | 今回の観察で新規の保存不能・データ消失は再現していない | 保存失敗・競合を扱う既存テストを維持する |
| P1 今日 | 縦長の紙面で予定とToDoが遠い。目次から対象の欄へ移動する | 中。描画順、スクロール、Tab移動を各幅で確認 |
| P1 タスク | 同じ頭文字の担当者を区別しづらく、次の作業を知るのに案件ノートを開く必要がある | 小。案件行の表示と読み上げの説明が対象 |
| P1 予定 | 日番号だけでは月境界が曖昧で、関連案件の見出しと抽出期間も一致しない | 中。日・週・月の往復、読み上げ名、全件への到達を確認 |
| P1 メモ | 索引を閉じると結果を限定した理由が見えにくい | 小。検索・色・閲覧中の紙片・解除後のフォーカスを確認 |
| P2 | 配色・余白・動きは、次回の索引一覧と日別明細の構成に合わせて検証する | 新たな演出を導入する前に高倍率・動きの軽減・実機読み上げを確認 |

指定された UI/UX Pro Max、Impeccable、Hallmark、Frontend Design、Apple Design、Web Design Guidelines は今回の環境の利用可能なスキルに見つからなかった。Astraによる構成比較、既存実装との照合、Playwrightによる実ブラウザの操作、同一データでの画面比較を使用した。

| 候補 | 得意な場面 | 負担が増す場面 |
| --- | --- | --- |
| 一日の時間軸に集約 | 今日の会議と空き時間の把握 | 時間未定の案件、確認待ち、手順メモを探すたびに別の索引が必要になる |

| 業務の目的ごとに紙面を設ける | 今日の判断、案件の再開、日程調整、記録の再利用に、それぞれ適した表示を使える | 画面を移るときに選択日、選択案件、検索条件、戻り位置を引き継ぐ設計が必要になる |

設計案には3番目を選んだ。たとえば、締切を過ぎた案件と受付時間の決まった予定では、最初に知りたい情報が違う。今日の入口では件数と目的を示し、詳細は案件・予定の既存画面に委ねる。紙面の見出し、罫線、余白でまとまりを示す。色と紙の意匠は残し、期限や選択状態は文字とフォーカス表示でも識別できるようにする。

## 今日　朝の判断

現行の `journalTodayV420` は、着手可能な案件を待機中の案件より先に並べ、上限6件を表示する。当日予定、受信・更新、未完了ToDo、待ち案件は別々の欄に載る。締切と会議時刻を確かめる利用者が、別々の欄を順に読み通す必要がある。

今回の実装範囲は、期日・超過、今日の予定、ToDoの件数を示す目的別の入口、選択した欄へのフォーカス移動、検索時のフィードバック。見出しや数字が指す母集団を揃える。特にToDoは抜粋の上限4件と未完了総数、案件は当日期限と期限超過を区別する。朝の確認作業では、目的を1回選ぶと該当欄を読めること、キーボードでも同じ欄から先へ進めることを確認する。

## タスク　中断した案件を再開する

`journalAtelierV420` には「今日触る」「確認待ち」「材料待ち」「依頼中」「完了間近」があり、同じ案件を複数のグループに複製しない。`journalIndexV425` は担当・状態・分類・期限・検索・並べ替えから案件を選び、読んでいた案件や位置の復元も扱う。

今回、机上の各案件行に担当者名を全文で記載し、期限を過ぎた行は日付に「超過」を添えた。着手可能で未完了の案件には、空欄を除く最初の未完了チェック項目を表示する。待機・保留・完了の行は次作業を出さず、チェック項目のない行にも次作業を補わない。長い次作業は2行まで見せ、全文は案件ノートで読む。担当者・状態・期限を件名と一緒に読み比べるときの情報量を抑えるためである。

確認課題は、長い担当者名が折り返せること、着手できる案件と待機案件で表示が切り替わること、キーボードで選んだ行の期限を読み取れること。索引一覧の列構成、待機理由の詳しい表示、一括選択・日付日誌を含む画面間の再構成は次回の候補。「材料待ちの対象案件を2操作で開く」「索引から詳細を閉じて元の件名へ戻る」は将来案と比較するための操作目標とする。

## 予定　空き時間を選び、変更後に戻る

`journalScheduleV425` は日・週・月を切り替え、共通の予定を担当・分類等で絞り込む。既存の空き時間候補、複数日にまたがる予定、日ごとの入力選択、変更後の復帰を含む。日では時刻と空き枠、週では複数日の比較、月では日付の選択を主目的に置く。スマートフォンで時間割の全列を詰める案は、短い予定の件名とタップ領域を圧迫する。選択日の時刻・件名が先に読め、残りの日も選べる構成を優先する。

今回の予定画面の実装範囲は、ミニカレンダー・月表示の日付ボタンの読み上げ名、月表示の曜日見出し、表示期間に対応する関連タスクの見出しと開閉操作。現在の表示期間に合う案件を確認し、必要なときだけ関連タスクを展開できることを検証する。

先の改修に向けた受け入れ課題は「日付を選び、その日の予定または空き枠を1回で開く」「複数日にまたがる予定の時間を空き枠に出さない」「編集から戻ったとき選択日・表示形式を維持する」。時間割の並べ替えや空き枠選択の再設計は次回候補とする。

## メモ　必要な記録を引き直す

`journal-display-v367.js` の `composeMemoIndex` は実在のカードから索引を作る。色は索引と紙片の両方を絞り込み、索引内のタイトル・分類検索は索引だけに効く。固定メモを先頭に置き、手動順・更新順・分類順・タイトル順を選べる。幅760px以下では索引を開閉する。

今回、開閉部の外にある既存の条件表示を更新した。索引を閉じても検索語と該当数・色条件内の総数が読め、選んだ色が索引と紙片の双方に効くことも分かる。同じ場所の解除ボタンで検索と色を解除する。すべてをカード本体の絞り込みに統一する案では、索引で候補を探しながら現在の紙片を読み続ける使い方が失われる。受け入れ課題は「色と索引内検索の併用状態で0件の理由を確認し、1操作で条件を解除する」「解除後に、表示していたカードとキーボードの操作位置を確認できる」。同名で分類の違う2件を選び分けるための索引項目の改善は次回候補。

## 実装の優先順と再開手順

1. **今日**。目的別入口と検索時の反応を、期限超過あり・当日期限のみ・0件・抜粋上限超えのデータで検証する。完了判定には実装差分と実行結果を用いる。
2. **予定**。今回の日付・曜日・関連タスクの変更を日・週・月で検証する。次に、今日から予定を開いて戻る経路と、空き枠から予定作成までの操作を測り、手順が多い箇所を特定する。
3. **タスク**。今回の机上の行について、担当者名、着手可否別の次作業、超過表示、キーボード操作を確認する。次回は机上と索引一覧で同じ案件を開き、担当・期限を見つける操作数を比較する。
4. **メモ**。今回の条件表示を、色条件と索引内検索の同時利用で検証する。次回は同名メモの再発見に必要な手がかりを調べ、索引項目の再配置を判断する。

各フェーズを再開するときは、JOURNALで表示していることを確認し、同じローカルデータで変更前後を比較する。幅390pxと1366pxで各課題を実行し、タスク名・時刻・メモ名の欠け、横スクロール、キーボードの戻り位置を記録する。メモは760pxと761pxでも開閉状態を確認する。実利用者の作業時間は未計測。
