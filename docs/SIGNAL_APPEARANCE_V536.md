# SIGNAL 表示モード・互換性設計（Ver.535–536）

## 目的と採用ルール

現行Release 304の業務機能を壊さず、ユーザーがクラシック/SIGNALを選択できる。
SIGNALに限り「ブライト（明色）」と「ミッドナイト（暗色）」を選ぶ。
既存ユーザーへの初期値はクラシック。旧デザインのCSS、アイコン資産、既存ナビゲーションを削除しない。

## 正本と所有者

| 資産 | 所有 | 変更範囲 |
|---|---|---|
| ui-design-d3l-v535.css | SIGNALと設定UIの見た目 | 新デザイン選択時の視覚表現のみ |
| ui-preferences-v536.js | 表示選択と端末内保存 | Firebase不使用。room/user毎にlocalStorage。デザイン変更時だけTodayの表示更新を依頼 |
| app.js | 既存の描画と集計 | Todayの構成と未設定時の表示順。保存・通信・業務処理は変更しない |
| index.html | 設定入口とdialogの静的DOM | 既存のユーザー・状態・分類管理画面へ委譲 |
| dialog-lifecycle-v239.js | 既存のdialog後方クリック制御 | wbSettingsDialogだけ明示的に追加 |
| release-manifest.js | 304のRelease資産正本 | CSS/JSを各1回登録。motion→mobile shell末尾の順を保護 |
| patch-responsibilities.json | 動的資産台帳 | 2つの独立した所有者を登録 |

### 個人設定の境界

- キー: `work-board-appearance-v536:<encode(room)>:<encode(user)>`
- 値: `{"design":"classic"|"signal","tone":"bright"|"midnight"}`
- 同じブラウザの同じルーム・選択ユーザー単位。異なる端末間では自動同期しない。
- 現行ユーザー名のローカル選択を参照するもので認証権限は変えない。
- 不明値、不正JSON、未保存はクラシック/ブライトへ戻す。
- 旧デザインを選択したときは新CSSが既存DOMへ作用しないようスコープを設定。

## 既存機能の保護

- ToDo追加フォームは製品の`renderTodoView`にて元々リスト上にある。位置や保存イベントは変更しない。
- スケジュールの「一覧／月カレンダー」は既存`renderScheduleView`の正本としてそのまま使用する。
- 今日パネルの保存済み表示順、ユーザー別の並べ替え・上下ボタン、ドラッグ代替を維持する。
- Firebaseデータ・ルール・接続・保存スキーマ、タスク/ToDoの編集・削除を改修対象に含めない。
- 既存SVGアイコンを上書きしない。表示用filterはnone。
- 新テーマでのみ装飾的な副題を非表示。絞り込み状態など判断に必要な表示は残す。

## D3「今日」画面の構成

SIGNALでは、既存のToday描画で作成したノードを再配置する。カードの複製、別の保存データ、別のFirebase購読は作らない。元のイベントを登録する前に構成し、その後は従来の操作処理へ委譲する。

- PC：左列に第1パネルと個人ToDo、右列に概要・第2パネル・お知らせ、下部に残り3パネル。
- モバイル幅：第1パネル→概要→個人ToDo→第2パネル→お知らせ→残り3パネル。概要は非操作要素で、操作可能要素の順序は維持する。
- 並び順が未設定の場合、SIGNALは「期限超過／今日の予定／今日までのタスク／未整理／空き時間」の順を初期表示に使う。クラシックは従来の予定先頭を維持する。
- 有効な保存順がある場合はその順を最優先し、上記5つの配置枠へ割り当てる。たとえば空き時間を先頭へ保存済みなら、SIGNALでも空き時間が左上に入る。D3の標準順で上書きしない。
- デザイン変更だけでは順序を書き込まない。並べ替え時も既存の`workBoardTodayPanelOrderV531`のルーム・ユーザー別キーを使う。
- ドラッグ方向の判定では、Todayの左右列をまたぐ場合も5パネル全体の順序を参照する。ToDo一覧のドラッグ判定は変更しない。

### 概要の数値と範囲

| 表示 | 集計元 | 絞り込み |
|---|---|---|
| 期限超過 | 既存Todayの`overdue` | Todayの担当者・分類・自分の担当条件 |
| 自分のToDo | `visibleTodos()`の未完了 | 選択ユーザー個人のみ。サイドバー条件の対象外 |
| 今日の予定 | 既存Todayの`schedules` | Todayの担当者・分類・自分の担当条件 |
| 確認待ち | 既存Todayの`openTasks`から状態「確認待ち」 | Todayの担当者・分類・自分の担当条件 |

既存の全体集計のラベルだけを変えず、Today自身の集計値を渡す。フィルター適用中は既存の条件表示とクリア操作を残す。

### 切替と再描画

`ui-preferences-v536.js`から、デザインが変わった時だけ`WORK_BOARD_REFRESH_TODAY_PRESENTATION_V536`を呼ぶ。Todayが描画済みの場合だけ既存のToday描画を再実行する。配色変更だけではノードを作り直さない。document/windowの新しいイベントリスナーや全画面MutationObserverは追加しない。

## 作業用評価ゲート

1. ProtocolとRelease Contract、Browser回帰、Firebase Emulatorが成功。
2. 旧デザインの既存Visual Snapshotが変わらないこと。
3. SIGNALの両配色で主要画面を確認。1920×1080、1366×768、390×844、320×800を重視。
4. ToDoの追加・並べ替え・完了、カレンダー/一覧切替、詳細dialog、設定・ユーザー変更を実際に確認。
5. Todayの初期順・保存済み順、左右列をまたぐ上下/ドラッグ、件数の意味、フィルター、再読込、保存レコード不変を確認。
6. PR同一HEAD成功と見た目の確認後にmainへの統合を判断する。mainおよびPagesの同一SHA成功はマージ後ゲートとして別途確認する。
7. 新モードの初期値はクラシック。公開後の利用者による選択は段階的。

## リポジトリ整理・削除方針

- 追加した実行ファイルはCSSとJSの2本。Today移植でも製品資産を追加しない。
- 根拠なく古いJS/CSSを削除しない。旧HTML/キャッシュ済みURLとの互換がある。
- 退役候補ごとに`requiredAssets`/`dynamicStyles`/`dynamicScripts`、DOM/JS参照、旧URL互換、およびPlaywright/Pages payloadを照合。
- 安全に退役可能なものは従来の`asset-retirement-inventory-v379`等の方式で別PRとし、実体ファイルと公開互換エイリアスを区別。
- タスク管理デザインと旧資産退役を同一PRで混在させず、切り戻せる変更単位を維持する。
- 分離QAブランチの試験用Workflowは本体PRへ取り込まない。

## 残る工程

Todayの主要な情報配置を移植する工程と、他4画面・詳細/設定の視覚整合、最終受入を分ける。D3モックの全画面移植が完了したとは扱わない。実際のテスト結果・対象SHA・画像確認はPRの検証記録で確認する。
