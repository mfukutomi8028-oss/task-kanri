# 恒久リンク登録・古い履歴・保留リンクの再設計（第3回独立レビュー対応）

対象SHA: 337e6ac1（第3回レビュー REVISE）。本書は、実装前に原因と修正後のデータフローを整理し、設計レビューを経て採用した設計を記録する。

## 1. 原因

| 指摘 | 根本原因 |
| --- | --- |
| 恒久リンクの登録認可 | リンクの書き込みをブラウザに許し、Rulesは「作成者=本人」と「業務記録が実在」だけを確認していた。業務記録IDはクライアントが任意に指定できたため、承認済み利用者は無関係な既存記録にもリンクを付けられた。業務データ `rooms/{room}` には認証がなく、「その記録がこのメッセージから正規に作成された」ことはRulesで表現できない。 |
| 古い履歴 | 対象から読み込み済み最古までを連続させるストアだったため、対象が古いほど取得件数が増え、上限300件を超えると移動できなかった。この要求の作業単位は308で、要求予算の上限304を超えており、本番では常に拒否される状態でもあった。 |
| 保留リンク | リンク登録の正本がブラウザにあったため、会話ID・メッセージIDを localStorage に保存し、端末側で失効・複数タブ・期限・件数を管理する必要があった。 |

## 2. 実装前の設計レビュー

当初案は「予約 → 作成 → 確定（confirm）→ 再開（resume）」の4段階だった。独立した設計レビューで、次の問題が指摘された。

- 同じミリ秒に発行したIDが連番になり、推測できる。
- 確定の応答が失われると、再送で別のIDが発行され、記録が重複する。
- 期限・件数・緊急停止によって確定前のリンクが失われる。
- 1回の確定で読み取りが多すぎる。
- 履歴ウィンドウ表示中に、未取得区間をまたいで既読になる。
- 新着でウィンドウが置き換わる。
- 取消された保存が件数枠を消費する。

そこで、レビューの代替案を採用した。**サーバーが記録IDを発行する同じ要求の中でリンクも書く**。確定・再開・保留状態は持たない。

## 3. 採用した設計

### 3.1 サーバー発行IDによる作成時リンク（recordReserve）

1. 作成画面で保存を押すと、業務管理ボードは既存の入力検証と確認ダイアログ（予定の重複、一括作成の確認）をすべて通す。その後、保存直前にメッセージ機能の `recordReserve` を呼ぶ。
2. サーバー（`security/messaging-record-origin-service.mjs`）が確認すること：
   - トークン
   - 端末承認（binding の approved・active）
   - 期待する personId
   - 会話が有効で、本人が所属中であること
   - 元メッセージが実在し、加入後で、未削除であること
3. サーバーは新しい記録IDを発行する。
   - 形式は Firebase push キーと同じ（時刻8文字＋乱数12文字）で、乱数は CSPRNG の72ビット。連番にはしない。
   - 件数：単発タスク・単発予定は1件、複数日予定は件数分（最大200件）。
4. 発行したIDのリンク `messagingV1/{room}/recordLinks/{task|schedule}/{id}` を先に書く。その後、本人の予約索引 `messagingV1/{room}/recordOrigins/{personId}/{requestId}` をトランザクションで記録する。索引があれば、そのリンクは必ず書かれている。
5. ブラウザは発行IDで、既存の保存処理（リビジョン0の新規作成、一括予定の単一トランザクション）を使って記録を作る。保存形式とUIは変えない。
6. 同じ作成要求ID（作成画面ごと・種別と件数ごと）で再送すると、索引から同じIDが返る。そのため、保存結果が不明でも記録は重複しない。
   - 再送時に、その発行IDの記録がすでにあり、作成者も同じなら、作成済みとして扱う。
   - 別の会話・メッセージ・種別・件数に同じ要求IDを使うと conflict になる。
7. リンクを予約できない場合（未接続・権限なし・上限）、利用者が選ぶ。
   - 「リンクなしで保存」：記録はリンクなしで保存する。
   - 「キャンセル」：入力を保持したまま中止し、接続回復後に再保存できる。

保証すること：
- リンクが付くのは、認可されたメッセージから新規作成するためにサーバーが発行したIDだけである。
- 既存記録のIDは指定する手段がない（要求に記録IDの欄がない）。
- ブラウザからの `recordLinks`・`recordOrigins` への書き込みは、Rulesで拒否する（`.write: false`）。

読み取り：従来どおり、各リンクの階層で、読む人の承認・所属・加入時点・削除・緊急停止をRulesが確認する。親階層からは読めない。

未作成IDのリンク：利用者が保存を取り消した場合など、記録が作られなかったIDのリンクが残る。記録がないため画面からは参照されず、リンクを一覧する手段もない。1人あたり7日間で50件（各最大200ID）までに制限する。

要求予算：作業単位は 24＋件数（最大224）で、上限304に収まる。緊急停止と端末承認の確認は既存のAPI境界を通る。

保護範囲（明記）：業務データ `rooms/{room}` は無認証のままである。本設計は業務記録の所有者認証を実現していない。作成後、その記録の内容は誰でも書き換えられる（既存の制約）。

### 3.2 対象中心の履歴ウィンドウ

- **取得方式：** `history` に `around`（対象ID）と `after`（カーソル）を追加し、`until`（対象から現在まで、300件）を廃止した。
- **around の範囲：** 対象の前24件＋対象＋後25件で、合計50件以内（従来の1ページ上限）。
  - 前側は加入時点より後から読む。同時刻の並びは (createdAt, id) で決める。
  - 1件多く読み、続きがあるかを判定する。
  - 対象が削除済み・加入前・存在しない場合は `missing` を返す（成功扱いにしない）。
- **after：** 新しい側を1ページ（最大50件）ずつ追加する。
- **認可：** 応答前の再認可、加入時点、削除済みの伏せ字は、通常ページと同じ処理を通す。
- **ストア：** ウィンドウ表示中は `hasNewer` で未取得区間を表す。表示中は次のとおり扱う。
  - 新着通知で最新ページに置き換えない。
  - 未取得区間をまたいで既読にしない（`markRead` は無視する）。
  - 送信すると最新に戻る。最新ページに到達すると通常表示に戻る。
- **画面：** 「ここから最新までのメッセージは未取得です」と、「新しいメッセージを読み込む」「最新に戻る」を表示する。検索では、未取得区間が検索対象外であることを表示する。
- **通信量：** 対象までの距離（300件、301件、4,950件以上）に関係なく、要求1回あたり最大50件。

### 3.3 保留リンク

保留状態そのものをなくした。ブラウザに残るのは、作成画面を開いている間だけ、メモリ上に持つ元メッセージと作成要求IDだけである。

旧候補が localStorage に保存した `wb-messaging-pending-links-v1|…` は、起動時に削除する。

| 場面 | 振る舞い |
| --- | --- |
| 再読み込み・PC再起動・通信断 | 端末承認と認証状態は変えない。復元するものはない |
| 権限失効・UID変更・利用者切替 | 作成画面の元メッセージ情報を消す |
| 複数タブ | 作成画面ごとに要求IDが別になり、互いに干渉しない |

## 4. 検査（修正前に失敗、修正後に成功）

- **Rules：** ブラウザからの `recordLinks` 書き込みを、有効な内容・既存記録・本人作成でも拒否する（旧Rulesでは許可＝失敗）。`recordOrigins` は読み書きとも拒否する。
- **予約サービス（実SDK・Emulator）：**
  - 無関係な既存記録を指定できない
  - 単発タスク・単発予定・複数日（3件・200件）
  - 再送・新端末（UID変更）で同じID
  - 並行再送で1組のID
  - 非所属・未承認・別人・加入前・削除済み・他会話・脱退・再加入・失効の拒否
  - 他の利用者との分離
  - 件数上限と期限
- **履歴（実SDK・Emulator）：** 5,200件の会話で、300件・301件・4,950件離れた対象へ移動する。結果は50件で、前後の追加取得、削除済み対象は missing、末尾到達を確認する。
- **Node：** 発行IDの非連番性、旧保留データの削除、API予算（224／58、上限304以内）、ストアのウィンドウ・未取得区間・既読抑止・最新復帰。
- **画面（Chromium・WebKit・320px／390px）：**
  - 作成時リンク
  - 通常起動・再読み込み
  - 既存記録にリンクなし
  - 別所属者・非所属者
  - 未承認・オフライン・失効と、失効後の再読み込み
  - 脱退・再加入・削除
  - 保存結果不明の再送
  - 予約不可時の選択
  - 開始日の失敗
  - 単発・複数日予定
  - 2タブ同時作成
  - 旧保留データ削除
  - ウィンドウ移動と未取得区間
