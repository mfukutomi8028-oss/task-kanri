# 共通開発標準：置換優先・単一正本・常時整頓

> この文書はプロジェクト固有の仕様ではなく、Web、PowerShell、VBA/Accessなどの開発にも再利用できる共通ルールです。現場固有の安全・互換性・データ保護要件は別途優先します。

## 目的と原則

**「過去の実装は履歴に保管し、現在の実行経路には正しい実装だけを残す」**。

1. **置換優先**：既存と同じ機能を変更するときは、原則として旧処理を直接修正・置換する。旧関数を残したまま新関数を後から呼ぶ、同じイベントを複数回処理する、後勝ちCSSで修正を積む、条件分岐やバージョン番号で古い挙動を永続させることを避ける。
2. **一機能一責務一正本**：業務判断、データ購読、保存、競合制御は所有者を一つにする。Classic/Modernの**異なる見た目を選べること**は要件上必要でも、裏側の業務処理・書き込みを二重実装しない。
3. **振る舞いを理解してから変更**：現行動作の成功・異常・境界条件を把握し、既存要件や保存形式を勝手に変えない。安全性を確認できない置換は、まずテストと依存調査を行う。
4. **常時整頓**：改修に関連する使われなくなった関数、import、イベント、CSS、設定、テスト、文書、未使用ファイルを同じ変更で整理する。関連しない大規模掃除は別の小さな変更として扱う。
5. **バックアップは実行コードと分ける**：ソースの旧版はGitの履歴・タグ・チェックポイント等で保全し、通常は`old/`、`backup/`、`*_old.js`、`v2_fix.js`など実行候補が増える保存方法を取らない。DBやAccessバイナリ、環境設定、業務データはGitだけでは保全できないため、別途復元可能なバックアップを取得する。

## 改修前の確認

- **正本の特定**：機能の入口、呼び出し元、実装本体、読取/書込所有者、依存モジュール、イベント/タイマー、設定、CSS、データ形式を確認する。現在有効な経路と使われていない経路を区別する。
- **現行の期待動作**：正常系、空・未選択、境界値、通信断、権限、競合、端末差、旧ブラウザ/旧保存データとの互換性を列挙する。テストが足りなければまず既存動作を固定する回帰テストを追加する。
- **変更の境界**：何を置換し、何を維持し、どのファイル/参照を削除し、どの利用者/画面/データに影響するかを明確にする。リリース、データ移行、切戻し手順を先に確認する。

## 実装時の置換手順

1. 変更前の期待動作をテストまたは検証記録で確認する。
2. **既存の実装を修正**する。複数の画面から必要なら、共通の所有モジュールへ移して呼び出し元を切り替える。単なる委譲ラッパーを残す場合も、そこで業務判断を重複させない。
3. 置換済みの旧分岐・旧ハンドラー・重複関数・不要な参照・未使用資産を削除し、対応するテストと文書も更新する。
4. ユニット、契約、統合、UI、セキュリティ、複数端末/競合など**変更によって影響する検証**を実施する。テスト側も意味が変わっていないか確認し、安易なskip・閾値緩和で合格させない。
5. 差分を確認し、**新旧の実行経路が意図せず二重に残っていないこと**を検証する。原因不明のテスト不安定性は「完全合格」とせず残課題として明記する。
6. 失敗時に旧コミット・復元可能なバックアップから切戻せるようにしてから、レビューと公開判断を行う。

### 例外：一時的な共存が必要な場合

破壊的なDB移行、旧URL・キャッシュ済みHTML、外部API契約、段階的切替、障害時の切戻しなどで旧処理を残すことはある。その場合は、**理由・責務の所有者・有効期間または削除条件・関連テスト・撤去担当/課題**を明記し、使う処理が不明な二重実装にしない。期限が決まらない場合も、撤去に必要な検証条件を定義する。旧コードを残すだけの「念のため」は例外としない。

### ファイル名・構成

- 既存の機能と同じ責務のファイルを、安易に`*-v556`や`*-new`として増殖させない。可能な範囲で安定した役割名を用い、既存の正本を置換する。
- ただし現在のプロジェクトの**公開URL、バージョン同期、古い端末のキャッシュ、テスト契約**などがバージョン付き資産を必要とするときは、参照調査なしに一括改名/削除しない。既存の大量ファイルを理由もなく一度にリネームせず、変更対象から安全に整理する。
- ディレクトリは役割を基準に分割する。役割のない汎用フォルダー、使われない抽象化、同じ責務を持つ複数実装を避ける。新規プロジェクトでは入口・業務ロジック・インフラ接続・画面・テスト・文書を区別する。

## 読みやすいコードとコメント

- 名前を読めば処理の目的がわかる関数/変数名にする。1つの関数に無関係な責務を詰め込まず、関数分割自体が目的にならないようにする。
- コメントは原則として**なぜこの処理・条件が必要か**、守るべき不変条件、失敗時の扱い、データの所有者、互換性の理由を記述する。「値を1加算する」等のコードを言い換えるだけのコメントは不要。
- 公開APIには用途・入力と戻り値・副作用・エラーを必要な範囲で説明する。特殊な日付処理、競合制御、権限制約には判断根拠を記す。
- 変更したコードと食い違うコメント・README・設計図・テスト名を放置しない。経緯はPR/コミット履歴に保管し、現行仕様の文書は**現在の状態だけ**を正しく説明する。
- 人間が見て理解できない複雑な条件や名前は、コメントで隠さずコードを簡素化する。

## Pull Request／受入ゲート

すべての改修で、次を差分・PR本文から追えるようにする。

| 確認項目 | 必須の証跡 |
| --- | --- |
| 何を変更したか | 目的、現行との差、対象範囲、保持する仕様 |
| どれを置換・削除したか | 旧関数/ファイル、入口、削除済み参照の一覧。削除不能なら理由・撤去条件 |
| 単一正本か | データ購読・保存・業務判定の所有者、二重登録/二重保存の不在 |
| 動作は保たれるか | 変更前の期待動作、例外系、境界、回帰テストと結果 |
| 戻せるか | ソースの復旧点、必要なデータバックアップ、切戻し手順 |
| 読みやすいか | 命名、必要な「理由」コメント、未使用コード/誤った文書の除去 |

変更の単位は、レビュー可能な一つの目的に絞る。大規模な整理と機能変更は、依存が強い場合を除き別PRにする。**CI成功だけで実運用受入や安全性が証明されたことにはしない**。

## この業務管理ボード固有の注意

- `main`、GitHub Pages、本番Firebaseルール・保存データは明示的な公開/変更許可がなければ変更しない。現在のClassicは業務データの単一所有者であり、Modernの描画・設定追加によって二重購読/二重保存を発生させない。
- 公開済みURLを旧HTMLや古い端末が参照している場合、**コードをGitから削除することと互換URLを消すことは別**。既存の公開互換マップ・ステージング生成方式、現行`release-manifest.js`と回帰テストを調べて撤去可否を決定する。
- ユーザーの明示要件である「ClassicとModernの見た目選択」は維持する。ただし双方の画面から利用する業務処理は共通化し、古い画面・新しい画面のどちらも見た目と業務処理の責務を分ける。
- 現在のFirebase Rulesは機密データ向けの権限制御を保証しない。テストで患者情報等を新たに投入せず、Emulatorと架空データを使う。
