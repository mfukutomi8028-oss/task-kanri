# 業務管理ボード — メッセージ機能 詳細設計

- 作成日: 2026-11-26
- 基準: Ver.675 / main `fdbe111e11f45cc747dc4af68f791609dcb3e63f`
- 状態: 利用者の方針承認を反映した詳細設計案。設計確認後に実装計画・テスト先行開発へ進む。製品コード、本番DB、認証設定、公開サイトは未変更。
- 対象: 共通の業務・会話ドメイン、先行UIはOrigin。Classic/JOURNALは正式ログイン導入後に展開。Paletteは対象外。

## 1. 目的と合意済み要件

LINE・Teamsに比肩する操作品質を目標としながら、汎用チャットの機能競争ではなく、業務の登録・相談・実行・完了・報告を一つのボードでつなぐ。会話は利用者間を主体とし、タスク単位で会話を量産しない。タスク内コメント、業務メモ、受信箱、個人付箋は各々の責務を維持する。

- 相手ごとに一意の1対1会話、自分宛て会話、任意名称のグループ会話・利用者招待・参加管理。
- 本文、引用返信、リアクション、編集・削除、既読・未読、通知、検索、下書き、確認依頼と確認済み、個人ブックマーク、グループ共有固定、お気に入り、ミュート、個人アーカイブと案件終了時のグループアーカイブ。
- タスク・予定・業務メモの件名参照添付（複数可）、詳細への移動と元会話への復帰、元業務画面からの共有、共有データ一覧。
- 画像・一般文書添付、クリップボード貼付、ドラッグ&ドロップ、サムネイル、ダウンロード、利用量管理、不要ファイル整理。
- 日次業務報告の編集可能な下書き生成（外部AI不要）。メッセージからタスク・予定を作成する業務連携も実装対象。優先度中の機能をスコープから削らない。
- Supabase Freeをファイル実体の保存先に採用。既存GitHub Pages/Firebase RTDBを維持。課金登録・自動アップグレードなし。利用者増加を想定。
- 第1回Origin公開 → ボード全体の正式ログイン・認可 → 検証・第2回公開 → Classic/JOURNAL展開。
- 音声/ビデオ通話、大容量動画、実行ファイル、外部AIへの業務本文送信、患者情報/機密情報の取扱いは対象外。

## 3. データ設計・責務

GitHub: ソース・静的サイトのみ。Firebase: 業務データと会話の正本。Supabase: 非公開Storage、添付の管理台帳・容量予約、認可済み添付API。管理キー・実データ・ファイル・ログイン情報をGitに入れない。

新規会話領域は旧 `/rooms/{roomId}` の外に独立させる。以下は論理名であり、Rulesの実現性検証後に物理スキーマを確定する。ルートread/write、旧rooms配下への会話保存を禁止。

| データ | 正本・主なキー・制約 |
|---|---|
| 利用者 | messagingAccessV1: 認証UID→不変personId、roomId、承認/失効状態。運用者だけが紐付け。表示名は表示属性で、認証・一意性・送信者判定に使わない。 |
| 会話 | messagingV1/{roomId}/conversations/{conversationId}: kind=direct/group/self、title、ownerId、status、lastActivity。directはソート済み2 personIdとroomの組で一意、selfもpersonIdごとに一意。管理者/所有者は一意性・同時作成を検証。 |
| 所属 | 会話とpersonIdごとのactive/role/joinedAt/leftAt、招待状態。権限の唯一の正本。退出・再参加は新たな閲覧境界。個別利用者の会話一覧索引は派生情報であり権限の代用にしない。 |
| メッセージ | 会話別messages/{messageId}: senderId、server createdAt、body(初期6000文字)、replyTo、refs、attachmentIds、revision、editedAt/deletedAt。送信要求IDを再試行で保持。作成時刻・送信者・所属を信頼境界で確定し変更不可。 |
| 個人状態 | 自分の既読カーソル、ピン留めした会話、お気に入り、通知ミュート、個人アーカイブ、ブックマーク。room/personIdで分離。他人の状態変更を禁止。 |
| 共有状態 | 固定メッセージ、確認依頼/確認済み、リアクション。固定やグループアーカイブは管理権限を検証。確認済みと既読は別契約。 |
| 添付実体 | Supabase private bucket、推測可能な元ファイル名や公開URLではなく不変attachmentIdから生成したパス。 |
| 添付台帳 | Supabase: roomId/conversationId/messageId候補、uploaderId、provider、objectKey、bytes、mime、表示ファイル名、sha256（整合性用）、state、createdAt。認可APIだけが予約/更新/削除。Firebaseに保存するのは参照IDと必要最小の表示情報。 |

共通ドメインをUIから分離する。identity/session、会話store、業務参照resolver、notification adapter、attachment storage adapterの責務を定義し、同じ処理を各テーマに実装しない。Supabaseを呼ぶのはstorage adapter/APIだけ。provider識別子を保存し、将来移行時は旧実体の検証・新実体へのコピー・参照切替・削除の順で行う。無断で他社クラウドに送信しない。

送信の整合性: クライアントは送信requestIdを固定、pending/sent/failedを明示。サーバー側で重複作成を抑止し、原子更新可能な範囲は原子更新する。タイムスタンプ同値をmessageIdで決着。再送・競合編集はrevision照合、失敗は入力を保持し通知。会話要約/個人索引/添付台帳は再構築可能にし、障害時に正本を上書きしない。RTDB親ノード全履歴のtransactionは避ける。認可・クエリ境界・索引更新の原子性をEmulatorで証明できない場合は実運用を止める。

## 4. 会話・業務UXの詳細

- 1対1は既存会話を再利用。グループは名前・招待対象・参加者一覧・招待状態。招待は本人が承諾、管理者が追加/除外/名称変更。所有者は移譲後に退出。脱退後はサーバー閲覧/書込不可（取得済み内容の回収は保証不可）。途中参加は原則加入後のみ、再招待も同様。管理者でも非参加会話を閲覧できないアプリ権限。グループアーカイブは閲覧可/送信不可、管理者が再開。個人アーカイブは相手に影響なし。
- 最新順会話一覧、個人/グループ/自分宛て、未読/お気に入り、検索。既読は会話が前面かつ実際に表示された範囲。自分の送信を未読に加えない。既読カーソルは単調前進し端末間同期、古い端末で戻さない。未読多数時は99+等の上限表示。ミュートは通知だけ抑制し未読は残す。受信箱は従来業務通知のまま、会話通知は専用入口へ。既存受信箱と連携する重要通知は重複生成しない。
- 引用は元ID＋安全な短い抜粋。削除/権限喪失時は抜粋・添付を表示しない。編集済み/削除済み明示。削除は墓標を残し本文/引用露出/添付アクセスを停止。リアクションは人ごとに一意・トグル。
- 確認依頼は送信時に任意指定、対象者を固定し「確認しました」の明示操作・日時を保存。送信者は対象者ごとの状況を確認。既読では自動確認しない。依頼本文変更は確認ラウンドを更新し旧確認を現行扱いしない。退会者は対象外化ではなく退会状態として区別。後からの参加者を既存依頼に勝手に追加しない。
- 個人ブックマーク・共有固定を区別。共有一覧はタスク・予定・メモ・画像・ファイル・URL、期間/種類フィルター、元メッセージへジャンプ。権限を失った項目は表示しない。
- 参照添付は roomId + type + recordId + 送信時の件名（アクセス許可がある場合のみ表示）。最新状態は既存canonical read selectorから取得。削除済み/移動済み/権限なしは内容を漏らさない表示に変更。参照添付は元データの閲覧権限を拡張しない。元業務から共有・会話へ復帰する際、会話ID・メッセージID・検索/スクロール位置を保持する。参照された業務を会話から更新するときは既存bridgeの編集・保存契約を使う。
- 日次報告は指定日/利用者、当日完了タスク（完了日時が取得できるもの）、当日の予定（実施と予定を区別）、進行中、補足。対象選択と手修正、参照添付、自動送信しない。完了日時を推測しない。業務記録の既存型を調査し、足りない情報は明示する。
- メッセージ→タスク/予定は既存新規作成フォームへ下書き渡し、ユーザー確認・保存。元会話へのリンクは権限確認付き、元の会話本文を無制限に転記しない。作成失敗・キャンセル時も入力/会話位置保持。
- 下書きは会話別、利用者/room別。個人下書きを他利用者へ復元しない。ローカルは必要最小限・保存上限あり、正式ログアウトやアカウント切替・失効で保護。通信障害時は未送信を明示・再送、ローカル保存成功を共有送信成功と誤表示しない。

## 5. Origin画面設計

独立した「メッセージ」入口、未読バッジ。専用ワークスペースとして PC: 左会話一覧・中央タイムライン/入力・必要時だけ右に共有一覧/参加者。右領域は閉じられる、既定では本文の横幅を確保。小画面: 一覧→会話→詳細へ画面遷移、戻ると元の選択と位置。320/390px、1366px、ライト/ダークを検証。

```
メッセージ [検索] [新規]
会話一覧         | グループ名 / 参加者 / 共有一覧
  未読・お気に入り | 日付区切り・メッセージ・既読
  個人・グループ    | [確認依頼] [業務参照カード]
  自分宛て         | [画像] [文書]
                  | 引用・下書き・添付・確認依頼・送信
```

会話履歴の読みやすさ、長文折返し、日本語IME（変換中Enterで送信しない）、誤送信防止、送信状態・読み込み/空状態・エラー・再試行、キーボード操作とフォーカス復帰、44px操作対象、コントラスト、reduced-motionを重視。新着で過去閲覧中のスクロールを奪わず「新着」導線。確認・固定・検索・共有データを埋め込むが常に全ボタンを露出させない。Hallmarkを統括、UI/UX Pro Max、Apple Design、Impeccable等を必要時に併用し、実際のUI検証とスクリーンショットレビューを行う。汎用チャットの画面を模倣するのでなくOriginのトーンを維持。

## 6. 添付・無料運用の詳細

設計値（初期の提案、運用計測で見直す。無料プランを変更しない）:
- JPEG/PNG/WebP、PDF、非マクロのOffice形式（docx/xlsx/pptx）、txt/csv等の許可リスト。実行・スクリプト・HTML/SVG・アーカイブ・マクロ文書・動画は初期不可。拡張子/MIMEだけを信頼せず、サーバーでサイズと形式の検査を行う。Office等はコンテナ構造も検証し、ダウンロード扱い。ウイルス検査が保証できない場合は明示、未検査を安全と表示しない。
- 最大5MB/件・5件/メッセージ。画像はクライアントで圧縮・再エンコードしEXIF等を原則除去、200–500KB目標、スクリーンショットの可読性優先。原本が必要な場合は上限内で選択。サムネイルは別保存時も容量に含め、無料枠外の画像変換APIを使わない。実行可能内容をブラウザ内で直接開かない。大ファイルは承認済み共有リンクで補完。
- 800MB（10進）をStorage使用＋予約合計の上限、600MBで警告、720MBで要整理。個人/グループの占有、直近利用、不要添付を見える化。初期の濫用対策は利用者ごとの送信頻度と暫定20MB/日アップロード上限を設定し、上限をUIでも説明。上限に達した場合は新規添付のみ停止し、本文/既存資料の参照は可能な範囲で維持。
- 添付API: 非公開bucket、直接の匿名upload/download/listは禁止。Firebaseの有効な本人トークンと最新承認・会話所属・加入時点を毎回確認。SupabaseのFirebase連携にはrole custom claimが必要な場合があり、Edge/API側の外部JWT検証は隔離実機で確認する。運用者がAdmin SDKで承認情報を設定し、課金必須のCloud Functionsを前提にしない。Admin/service-roleキーはサーバー秘密のみ。RTDB権限確認に全権Adminをブラウザへ渡さず、本人のトークンによるRules適用読み取りを優先。必要なバックエンド書込みは限定サービス主体・許可パスで実現性検証する。
- 容量の整合性: Postgres transactionで同時予約を制御し、実際に受信したバイト数をサーバーで上限検証。初期は5MB以下のサーバー検証経由でuploadし、直アクセスによる申告サイズ偽装/予約迂回を許さない。失敗/中断は期限付き予約を解除し孤立実体を清掃。予約→uploaded→ready→attached→deleting/deleted の状態契約。ファイル参照はroom/conversation/owner/requestIdと一致したready実体のみ信頼し、RTDBへの参照登録前後の障害を照合できるようにする。実体を失った参照はエラー表示し、既存メッセージを失わない。削除は先に新規閲覧を停止、実体削除と容量返却は確認後。自動で古い必要資料を消去しない。
- 取得は会話所属を確認した認可API経由を既定とする。利用量をバイト単位で保守的に計上し、アプリ配信の月間目安4GB（uncached側の余裕確保）で警告/制限。Supabase公式の組織全体通信量や内部経路の計上は別に監視。必要時のみ表示・同じ許可内での短期メモリキャッシュ、サムネイルの遅延読み込み。期限付きURLを将来使うなら短時間・最小範囲、発行後の即時個別失効は保証しない。公開URLや恒久URLをメッセージに保持しない。
- 画像/文書削除・バックアップ/復元・利用停止時の再開・移行手順を実装計画に含める。管理者の手動エクスポートを基本に、メタデータと実体のハッシュ整合を確認し、患者情報や秘密を入れない。無料プランでは自動バックアップや稼働保証を前提にしない。未使用による一時停止へのUI対応。

## 7. 人数増加・負荷

2026-11-26公式確認: Firebase Spark RTDBは1GB保存/10GB月間ダウンロード/100同時接続。100は登録者数ではなくタブ/端末等の同時接続で、既存業務ボードと共有する。Supabase FreeはStorage 1GB、通信5GB uncached + 5GB cached（組織で共有）、DB 500MB、Edge Functions月50万呼出、未使用1週間で停止する場合あり。いずれも将来変更あり。実環境の契約/消費量は未確認。

参考試算（1人あたり月22営業日・画像2件/日×200KB、文書2件/月×2MB、削除なし。サムネイル・既存使用分を除く概算）:

| 利用者数 | 添付増加/月 | 800MBまで |
|---:|---:|---:|
| 2 | 25.6MB | 約31か月 |
| 10 | 128MB | 約6.3か月 |
| 25 | 320MB | 約2.5か月 |
| 50 | 640MB | 約1.3か月 |
| 100 | 1280MB | 1か月未満 |

登録100人の設計検証を目安とするが、100人の無制限無料運用を約束しない。実測値で容量、既存RTDB利用量、ダウンロード、同時接続、Edge呼出を確認し、課金せずに上限対応（整理/容量調整/保存先の再評価/機能制限）を選べるようにする。

- 初期の一覧は会話要約だけ、最新メッセージ50件（過去50件ずつ）、古い履歴の取得上限・カーソル。active会話のみライブ購読、一覧の変更は要約に限定、非表示/利用者切替で購読を解除。既存Firebase接続を再利用しテーマごとに追加接続しない。全room購読・全履歴ダウンロード・全画像先読みを禁止。
- RTDB Rulesはクエリ制約（createdAtのstartAt、上限、順序、単件閲覧のjoin境界）を要求。加入時刻と同時刻のメッセージは厳格境界（加入後）を採用。同時送信/参加/退会・再招待時にもサーバー判定。Rulesはフィルタではないため、一括read許可で子の過去情報を守ろうとしない。必要な索引は.indexOn。検索・共有一覧は許可済みの範囲のみ、期間・件数・ページング明示。初期は会話/参加者名・本文・件名・送信者・日付の検索、古い範囲は利用者の操作で追加検索。検索を全件済みと誤表示しない。必要なら将来検索索引を追加。
- 個人の既読はカーソルを基準にし全メッセージ×全参加者の無制限複製を避ける。確認依頼のみ対象者別に記録。通知のファンアウトは必要時だけ、既存の共通通知所有権を崩さない。
- Emulator/fixtureで登録100人、1人あたり100会話、1会話10,000メッセージ、同時50セッション相当のシナリオを用い、取得件数、再接続、重複送信、権限越境、リスナー数、レスポンス、負荷を計測する。これは設計目標で本番の人数保証ではない。

## 8. 第1回公開と正式ログインの境界

利用者の指定: 現在2名、扱うデータは他者に見られても差し支えないものに限定。第1回公開を全体ログイン導入より先に行う。これを維持するが、URLの非周知だけでは、濫用・なりすまし・無料枠枯渇を防げない。

設計提案: ボード全体のログイン画面は先行しない。新規会話領域だけに、バックグラウンドのFirebase匿名Auth UID（端末/ブラウザの仮ID）を利用し、運用者が帯域外で本人と端末を確認してUID→personIdを承認登録する。新端末・ブラウザデータ消去時は再承認。許可前は会話/添付の読み書き不可。既存利用者選択が承認personIdと一致しなければメッセージを閉じ、なりすましを防ぐ。表示名選択による権限付与やグループ自己追加を認めない。UIDを知ること自体ではログインできない。端末承認の方法と再登録は手順書化。第1回公開時は「限定試用」、実データは非機密に限定。

この暫定の本人識別は正式アカウント登録ではない。正式認証工程で既存の承認済personIdへ正規Auth UIDを明示的・安全に紐づけ、全端末の旧資格を失効させる。匿名UIDと表示名から自動的に本人と断定しない。既存会話ID・メッセージ・所属・確認・ブックマーク・添付はpersonId基準で移行/維持する。旧DBのroomsV2移行は既存NO_GO解除・バックアップ/復元試験・承認が必要。旧経路を停止し、旧キャッシュ/旧端末からのアクセスを検証する。

暫定認証を実現できない場合、初回公開は架空データの試用モードに限定する。匿名の公開bucket/全許可Rulesに切り替えて出荷しない。正式ログイン後も患者情報等の格納は別途組織承認と安全性検証が必要。
