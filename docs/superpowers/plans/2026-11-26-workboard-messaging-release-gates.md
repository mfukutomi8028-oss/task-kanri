# Origin messaging: release candidate gates

2026-11-26 — implementation branch only. Do not publish with the feature enabled until all release gates below are verified.

- Browser runtime modules now live in the repository root (single source). The isolated preview retains only the fixture and entry HTML. Production config is disabled by default; the shared legacy board starts without loading Firebase Auth or messaging modules.
- Origin's header entry uses the existing canonical Firebase app and read-only business projection. First explicit use restores the Firebase Auth session and only signs in anonymously if no account is present. Device approval remains a server-side requirement. Do not use a selected display name as proof of identity.
- The approved Firebase Rules fixture is **isolated**, with no legacy rooms. Never deploy it directly. Export the actual live Rules securely, back them up, compose a separate candidate via `node security/compose-messaging-rules.mjs <live-rules-export.json> <new-candidate.json>`, review the exact diff and exercise both existing rooms and messaging in an emulator. The script deliberately rejects broad root grants and previously different messaging rules. Do not commit the live export.
- Existing legacy rooms may still have permissive access. This composition preserves their current rules rather than redesigning the legacy authentication model. Never store patient data in the messaging system.
- The deployment candidate must be reviewed independently; confirm current exact-head Protocol, authorization, Firebase, and browser regression jobs. Verify the deployed API and binding/roster approval using two synthetic accounts, including denied/revoked accounts and attachment upload/download if enabled. Verify the allowed HTTPS API endpoint and server-only secrets before configuring the client; do not place credentials in Git.
- Origin now keeps a single authorized unread-summary session after the first explicit messaging launch, even when the workspace is closed. The message body view and history store are disposed on close. The header badge totals unread messages and pending invites, marks partial counts, and is cleared on identity/config changes. No OS push or notification when the board tab itself is closed. New memberships/invites are discovered at the 60-second visible-board refresh. The initial 100-conversation monitoring bound remains; larger directories are partial, not exact totals.
